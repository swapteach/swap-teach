Comprehensive Specification & Operational Benchmark Guide: Database Systems Course Term Project

1. Course Curriculum Integration & Strategic Grading Framework

The Database Systems course is designed to bridge the gap between abstract relational database theory—such as relational algebra, functional dependencies, schema decompositions, multi-valued dependencies (A \twoheadrightarrow B), BCNF/4NF normal forms, and transaction isolation levels—and high-performance software engineering in modern production environments. While written examinations evaluate a student’s capacity to manually execute theoretical procedures like chase tests, closure calculations, or algebraic query transformations, the term project serves as the capstone applied component of the curriculum. It forces student engineering teams to synthesize system architecture, multi-tier client-server topologies, user interface design, and backend database administration into a unified, functional software platform.

Course Evaluation Distribution Breakdown

To align student effort with real-world engineering competencies, the academic evaluation structure assigns significant weight to practical execution alongside traditional testing:

Assessment Component	Weight	Key Evaluation Focus
Term Project (期末專題)	40%	Comprehensive application design, database engineering, external competition participation, live demonstration, and empirical peer review.
Midterm Examination (期中考試)	30%	Theoretical mastery of Relational Algebra, SQL query syntax, E/R diagram translation, and core schema design.
Final Examination (期末考試)	30%	Advanced theoretical concepts, including BCNF/4NF normalization, chase tests for lossless join decomposition, multi-valued dependencies, and transaction isolation anomalies.

Analytical Evaluation ("So What?")

A 40% weighting allocated to a single term project fundamentally alters student learning behaviors. In traditional computer science pedagogy where written exams account for 70% to 80% of the grade, students frequently resort to passive memorization and localized problem-solving without understanding how database engines behave under production application loads.

By making the practical term project the single largest grading component (40%), students are incentivized to prioritize system architecture, data modeling, concurrency handling, and API integration over passive test preparation. This structural distribution ensures that theoretical knowledge evaluated during exams directly informs architectural decisions made within the project.

For instance, understanding the mechanics of transaction isolation levels (SERIALIZABLE versus READ UNCOMMITTED) tested on examinations is precisely what prevents runtime lost updates or dirty reads in a student's concurrent mobile backend API. Similarly, mastering functional dependencies and Chase tests ensures that students design losslessly decomposed schemas that eliminate update anomalies when scaling their application database.

This strategic alignment between grading incentives and practical software architecture leads directly into the explicit technical mandates established for the project.

2. Architectural & Technical System Mandates

To ensure that student projects reflect modern software engineering standards rather than static classroom exercises, the course mandates a set of non-negotiable architectural constraints. These engineering baseline requirements force student teams to confront modern infrastructure challenges, such as multi-tier network latency, automated data ingestion, client-side memory constraints, and concurrent transaction management.

Core Engineering Specifications

All term project submissions must strictly adhere to the following technical parameters:

* Platform Deployment: Mandatory implementation of a mobile APP or tablet APP targeted for Android or iOS client devices (e.g., using Flutter or native mobile frameworks).
* Database Management System (DBMS): Open selection of DBMS engine (unrestricted choice; teams may select relational engines such as PostgreSQL/MySQL or non-relational engines based on domain requirements).
* Networked Infrastructure: Strictly MUST be a networked, multi-tier online application; single-machine or offline standalone implementations are explicitly prohibited.
* Artificial Intelligence (AI) Integration: Mandatory integration of creative AI capabilities tailored specifically to enhance the core application logic.
* Data Scale & Ingestion: Ingestion and active management of at least 200,000 records (20W+ records) sourced directly from Public/Open Data APIs or custom web scrapers.
* Version Control: Mandatory open-source or managed repository hosting and version control on GitHub.
* Department Hardware & Infrastructure Loans: Student teams are entitled to request hardware resources, consisting of one department tablet per group and one Virtual Machine (VM) instance, by submitting a formal application to Teaching Assistant Li-Wen (力文助教).

Reference Architectural Benchmark: "SwapTeach: A Campus Skill-Exchange App" (換你教－校園技能交換 App)

To ground these mandates in a concrete software blueprint, the course provides SwapTeach as an exemplary reference architecture. SwapTeach addresses campus peer-to-peer learning through a multi-tier engineering stack:

* Technology Stack: Mobile client built in Flutter (iOS/Android), backend application server powered by Python FastAPI, and database tier driven by PostgreSQL.
* Core Architectural Innovations:
  1. Graph Topology Matching: Beyond 1-on-1 direct skill trading, the server executes a directed graph search algorithm to identify circular matching loops (A \to B \to C \to A), where User A teaches B, B teaches C, and C teaches A.
  2. Time Coin Transaction Ledger: Implements an hour-for-hour exchange ledger where teaching 1 hour earns 1 Time Coin. The database enforces strict transactional consistency to manage currency balances without race conditions.
  3. AI Integration: Connects to Large Language Model (LLM) APIs to automatically generate tailored structured lesson plans (AI 學習計畫) based on user skill gaps and create post-class review quizzes (AI 課後回顧) from user session logs.

Operational & Technical Analysis ("So What?")

Enforcing a mandatory 200,000-record minimum dataset combined with a multi-tier client-server networked architecture transforms the project from a basic user interface prototype into a rigorous performance engineering challenge. Processing 200,000+ records exposes the immediate systemic consequences of flawed database design:

1. Schema Normalization (BCNF / 4NF): Naive single-table schemas containing multi-valued dependencies (A \twoheadrightarrow B) experience massive data redundancy and severe update anomalies at 200,000 records. Structuring tables into BCNF/4NF is essential to eliminate duplicate data storage and maintain referential integrity across mobile update requests.
2. Indexing & Join Optimization: Unindexed queries across 200,000 records trigger full-table scans that choke server CPU and memory. Teams must construct strategic composite B-Tree indexes to accelerate multi-table relational joins (R \bowtie S) and filtered aggregate queries (GROUP BY), maintaining sub-second API response times.
3. Server-Side Pagination: Transmitting raw query results of 200,000 records over mobile wireless networks causes socket timeouts and crashes client application memory. Server-side SQL pagination (LIMIT / OFFSET or keyset pagination) is required to deliver chunked JSON payloads to mobile endpoints.

Meeting these stringent architectural baselines requires rigorous task execution and structured timeline tracking across the academic term.

4. Student Peer Review Framework & Classroom Governance Rules

To foster objective evaluation, prevent grade inflation, and cultivate critical technical evaluation skills, the course uses a peer-driven review model. Student teams present their midterm proposals and final systems before the entire student body, who evaluate their peers under strict administrative governance rules.

Peer Grading Mathematical Formula

The peer evaluation score for any presentation milestone is calculated using the following mathematical formula:

\text{Peer Score} = 100 \times \left(1 - \frac{\text{Total "X" Marks Received}}{\text{Total Evaluators}}\right)

Where:

* Total "X" Marks Received represents the cumulative count of negative/rejection marks assigned to the presenting group by voting peer evaluators.
* Total Evaluators represents the total number of valid student evaluation forms submitted during that session (e.g., 68 submitted forms out of 70 enrolled students).

Operational Scope: This exact peer evaluation formula applies to BOTH the Midterm Proposal Presentation (5%) and the Final Presentation & Live Demo (20%). Furthermore, for teams displaying project results or competing externally, the submission of the formal Reflection Report (心得報告) serves as a required supplementary deliverable to finalize these peer scores.

Presentation Day Operational Governance Rules

To ensure fairness, efficiency, and professional decorum during presentation sessions, the following operational rules are enforced without exception:

* Student-Elected Moderator: Presentation flow and session transitions are managed entirely by a student elected by peers to serve as master of ceremonies/host.
* Strict Punctuality & Late Arrival Penalty: All group presentations occur within a single dedicated class session. The moment presentations begin, evaluation forms are permanently locked and will no longer be distributed. Late-arriving students are treated as absent.
* Restroom Policy & Score Confiscation: Restroom breaks during presentation sessions are limited strictly to 2 minutes. If a student is absent during any single group's presentation, their evaluation sheet is immediately confiscated, they are marked officially absent, and all forced "X" penalties are charged directly against their own personal project score.
* Absentee Penalty: Students marked absent are barred from evaluating peers and will automatically receive the maximum negative "X" penalty count charged directly against their personal grade.

Evaluator Quotas & Quality Requirements

* Forced "X" Quota: To counteract universal high-scoring collusion, every student evaluator MUST assign a minimum of 5 "X" marks across all group presentations. This baseline quota is derived from a standard cohort of 15 presenting groups:

\text{Forced "X" Quota} = 15 \text{ groups} \times \frac{1}{3} = 5 \text{ "X" marks}

(Note: If the total number of presenting groups increases, the required forced "X" mark quota scales upward proportionately).

* Mandatory Written Justification: Every assigned "X" mark MUST be accompanied by an objective, written technical or presentation critique on the evaluation sheet. Arbitrary, subjective, or personal excuses (e.g., "I dislike the speaker," "unpleasant speaking voice") are strictly forbidden and will be invalidated by the instructor.

Topic Rejection & Revision Action Thresholds

Based on a standard benchmark cohort size of 70 enrolled students yielding 68 valid submitted evaluation forms, projects receiving high counts of negative "X" marks trigger mandatory academic interventions:

Received "X" Mark Count	Percentage Rejection Threshold	Mandatory Academic Outcome / Governance Action
> 25 "X" Marks	~36.8% Peer Rejection	Official Recommendation to Change Topic (建議換題目): System design exhibits major conceptual flaws or minimal domain value; scope revision strongly advised.
> 34 "X" Marks	> 50.0% Peer Rejection	Mandatory Topic Rejection & Re-proposal Required (需重提): Project rejected by an absolute majority; team must submit a completely revised project proposal.

"X" Count:  0 ─────────────── 25 ───────────────── 34 ───────────────────── 68
Status:     [  Passed / OK  ] [ Suggest Change Topic ] [ Mandatory Re-Proposal ]


Analytical Evaluation ("So What?")

Without strict governance rules, student peer grading rapidly degrades into reciprocal grade inflation, where every team awards maximum scores to every other team.

By enforcing a forced "X" quota (minimum 5 "X"s) alongside mandatory written technical justifications, students are forced to critically evaluate their peers' database normalization, system architecture, UI responsiveness, and live demonstration performance.

Furthermore, strict administrative penalties associated with missing presentations, restroom delays (>2 minutes), or late arrivals instill professional discipline. The action thresholds (>25 "X"s for topic change recommendation; >34 "X"s for mandatory re-proposal) establish an immediate quality control loop, ensuring that unviable concepts are filtered out early in the semester.

The operational reality of these classroom governance metrics is best understood through historical peer evaluation dataset performance.

Conversely, top-performing applications integrate complex transactional relational schemas, custom graph or matching algorithms, real-time filtering across multi-table joins, and domain-specific analytical capabilities.

To avoid project rejection, teams must maintain internal accountability and administrative discipline from the outset.
