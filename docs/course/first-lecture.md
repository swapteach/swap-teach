## 專題要求

- **最好做 APP。** 老師偏好 APP（Android 資源比較好找）。為了參加比賽可以不做 APP，但要說明為什麼這樣比 APP 更有創意；**「我想做網頁」而沒有理由，老師不接受**。原因是網頁太容易抄現成的東西。
- **先查有沒有人做過。** 決定題目前，先查別人做過什麼、做到什麼程度。如果已經有人做好，直接用別人的就好，不需要重做。
- **AI 可以用別人的。** 自己寫或用別人的 AI（例如呼叫 API）都可以，重點是在 API 之上做出有趣的應用。老師希望更有創意，他認為以前的題目大多不用心。
- **資料必須合法取得。** 自己爬的、政府公開資料或其他來源都可以，但要合法。
- **資料量要大。** 老師的理由是：只有一兩百筆的話用檔案就好，不需要資料庫。⚠️ 待確認：逐字稿寫「220 萬個欄位」，投影片寫「20 萬筆」；可能是語音辨識錯誤，也可能是「欄位」與「筆」的差別。
- **連線版。** 單機版容量不夠，而且 AI 本來就在遠端。
- **伺服器。** 系上 VM 有實體 IP（140.136.x.x），在家也能連；也可以使用免費的雲端服務，說明清楚即可。
- **GitHub。** 最後要把 repo 網址交給老師。程式碼如果真的不能公開，可以用自己的私人主機（例如 NAS）。
- **組數。** 老師希望不超過 15 組（系上平板與 VM 約各 30 部）。⚠️ 待確認：逐字稿提到「如果你要三個（人）我就成績打九（折）」，意思不確定。
- **語言。** 老師說 Android 教科書不一定要用指定版本，「只要你可以上手都 OK」；沒有限制一定要用 Java。⚠️ 仍需向老師確認是否接受 Flutter。

## 期中與期末發表

- **期中報告是進度報告。** 原本學期初的提案改到期中考後一週，讓大家有上半學期決定題目。
- **同學互評，老師不參與。** 老師現場不說話，避免被說帶風向。
- **評分三個面向：完整度、創意、可用性。** 老師會分別評這三項。
- **打 X 要有合理理由。** 老師接受的例子：介面不夠好看、可用性低、資料庫筆數不對、沒有用 GitHub、**看不到資料庫設計的過程**。不接受的例子：討厭報告者、跟對方有仇。
- **不可以拉票或串通。** 例如請別人「不要打我們 X」，老師會把 X 算到這些人那一組身上。
- **「屍體」不評分。** 發表時沒有成品，或 Demo 到一半當掉、轉圈轉不出來，都算「屍體」，老師會請同學不要評這一組。沒有成品的話，期中期末考再高分也不會及格。
- **發表前已入圍或得獎可以說出來**，讓同學知道。
